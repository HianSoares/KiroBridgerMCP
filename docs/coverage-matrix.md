# Upstream MCP coverage matrix

Generated by `scripts/build_coverage_matrix.py` from `src/soc_bridge/upstream_registry.json` (audited handlers and complete `tools/list` of the versions below). Do not edit by hand.

- IBM QRadar MCP: https://github.com/IBM/qradar-mcp.git at `60ca119ecc05`, committed 2026-10-05.
- Trend Vision One MCP: https://github.com/trendmicro/vision-one-mcp-server.git at `2d137401c26e` (v0.9.0), committed 2026-09-23.
- Policy version `2026-10-15.2`. The effect comes from the handler (HTTP method, client calls, registration), never from the tool name or `readOnlyHint` alone.

Coverage levels, kept separate:

- **Catalogued**: every row. The tool is in the audited handler catalog and in the complete `tools/list` of that version (Vision One write tools are announced only without `-readonly`). A given installation may not announce it (feature toggles, toolsets, version); `upstream_inventory` reports that at run time.
- **Route** (supported and routable): `query` tools run through `upstream_query` on soc-bridge-readonly; `change` tools only through the separate soc-bridge-change server; `unsupported` tools have a reason.
- **Policy**: query tools are enabled. Change tools are blocked by policy by default: they need `SOC_BRIDGE_ENABLE_CHANGES=1`, the tool in the policy file and a human approval typed in a terminal per call.
- **Curated workflow**: tools the investigation workflows call automatically when their trigger applies.
- **Contract checks**: the audited schema is a valid JSON Schema, matches the audited announced contract, and the tool has exactly one route enforced by the gate. This does not execute the tool.
- **End-to-end (synthetic)**: called through the bridge against a synthetic MCP server that reproduces the product's response format. All other tools are not exercised end to end, so their functional behavior is not proven by tests.
- **Real product**: no upstream_* call has been executed against a real QRadar or Vision One by this work. That validation needs customer credentials.
