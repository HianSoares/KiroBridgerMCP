# Access to every upstream MCP tool

The bridge reaches every tool of the audited versions of the [IBM QRadar MCP](https://github.com/IBM/qradar-mcp)
and the [Trend Vision One MCP](https://github.com/trendmicro/vision-one-mcp-server) through an audited registry.
Read tools run from `soc-bridge-readonly`. Tools that change state or send data out run only from a separate
server, `soc-bridge-change`, which is disabled by default and needs a human approval for each call.

| Audited version | Tools | Query (`upstream_query`) | Change (`soc-bridge-change`) | Unsupported | Pending review |
|---|---|---|---|---|---|
| IBM QRadar MCP `60ca119` (2026-10-05) | 83 | 53 | 30 | 0 | 0 |
| Trend Vision One MCP `2d13740` (v0.9.0) | 349 | 202 | 137 | 10 | 0 |

The per-tool view, with categories, effects, pagination, dependencies and test evidence, is in the
[coverage matrix](coverage-matrix.md). These totals describe the audited code. They do not prove that a given
installation, license or API key allows the tools; `upstream_inventory` and the error categories report that at
run time. No upstream_* call has been executed against a real tenant yet (see [Validation status](#validation-status)).

## Architecture

```text
Kiro ── soc-bridge-readonly ── upstream_tools / upstream_tool_details   (registry search, no network)
                            ├─ upstream_query / upstream_download      (gate → one upstream session → one call)
                            └─ upstream_inventory                      (complete tools/list vs registry)
Kiro ── soc-bridge-change (disabled) ── change_request → human approves in a terminal → change_execute
```

- **Registry** (`src/soc_bridge/upstream_registry.json`). It is generated by `scripts/build_upstream_registry.py`
  from two inputs: the handler catalogs (`docs/coverage/*-mcp-tools.json`, extracted by
  `scripts/upstream_catalog.py` without importing or running upstream code) and the complete paginated
  `tools/list` of each server (`docs/coverage/*-tools-list.json`). For every tool it records:
  - the effect and the evidence for it (basis);
  - the access path;
  - the validation schema (for QRadar, the handler schema with its ranges and enums, which the announced schema
    drops);
  - the announced schema, used for drift checks;
  - the HTTP method and path;
  - the pagination the handler actually forwards;
  - the output format and product dependencies.
- **On-demand dispatch instead of one MCP tool per upstream tool.** The 432 schemas take about 410 KB, which
  would crowd the model context in every Kiro session. One generic dispatcher also keeps a single gate: exact
  names only, schema validation, the effect policy and contract checks. Kiro configures
  `autoApprove`/`disabledTools` per server, so the dispatch tools sit on the read-only server and the change
  tools on a separate server. The two catalogs share no names; the `platform` argument still namespaces every
  call. The longest upstream name has 61 characters, inside the usual MCP client limits. Upstream tools are
  never re-registered under new names.
- **Effect policy** (`src/soc_bridge/upstream_policy.py`). The effect is decided from the handler, never from the
  name, a verb or `readOnlyHint` alone:
  - QRadar: a `GET` that only calls `client.get` and is not marked approval-required is a read. `validate_aql`
    is validation, and `create_ariel_search` creates a search job, which is a read of data. `dns_lookup` and
    `whois_lookup` send the value to external services, so they are changes.
  - Vision One: a tool registered as read that issues `GET` is a read. Ten tools are registered as read but
    post data: seven Terraform/template generators, one service-gateway password generator, and
    `aisecurity_guardrails_apply`, which submits content. All ten are changes. Eleven tools annotated as both
    `readOnlyHint` and `destructiveHint` are plain `GET`s, so they are reads.
  - Anything that does not match these rules is `pending_review` and cannot be called.
- **Vision One containers.** Each query starts the official image with `-readonly=true` and only the requested
  tool's toolset, so the container cannot register a write tool. Change calls start it without `-readonly`, and
  read-registered generators keep `-readonly=true`.
- **QRadar.** The bridge only talks to a loopback `http://127.0.0.1:<port>/mcp`, with proxies ignored. The
  QRadar MCP has feature toggles but no read-only mode, so the gate is the only barrier on the read-only path.
  Keep the QRadar MCP itself bound to loopback.

### Per-call checks (`upstream_query`)

1. The platform is `qradar` or `vision_one`, and the tool name matches exactly (`^[a-z0-9_]{1,80}$`; no
   normalization, prefixes, paths or lookalike characters).
2. The tool is in the registry, verified and supported, and its effect is `read`, `validation` or `query_job`.
   Otherwise the call is refused with `upstream_call_attempted: false` and no session is opened.
3. Arguments are validated against the audited schema:
   - unknown properties are rejected;
   - the limit is 64 KB;
   - errors name the rule, never the value;
   - a parameter the handler declares but does not send is refused (`workbench_alert_notes_list.skipToken`).
4. One session is opened. The complete paginated `tools/list` must announce the tool, and its announced schema
   must match the audited contract structurally. If not, the result is `tool_absent`, `discovery_incomplete` or
   `contract_changed`, and no call is made.
5. Exactly one `tools/call` is made, followed by output normalization:
   - JSON or text;
   - a Trend `ETag`/`Operation-Location`/`Location` block becomes `response_headers`;
   - binary bodies are returned as metadata only (sha256, bytes, MIME); `upstream_download` saves them;
   - output is bounded, with `output_truncated` and item counts.

### Outcomes and error categories

| Outcome | Meaning |
|---|---|
| `ok` | Complete response for these arguments. |
| `partial` | The handler indicates more data (full Range page, `nextLink`, `nextBatchToken`) or the bridge truncated the output. |
| `empty` | No item matched this query, filter and window. Not proof of absence elsewhere. |
| `empty_response` | The call succeeded with no content. |
| `error` | See the category below. Errors are never turned into empty lists. |
| `refused` | Not sent upstream (`policy_blocked`, `unknown_tool`, `pending_review`, `unsupported`, `invalid_arguments`, `configuration`). |

Error categories:
- `invalid_arguments` (HTTP 400/422 or a known validation message);
- `authentication` (401);
- `permission` (403);
- `permission_or_license` (403 whose body mentions a license or entitlement);
- `not_found`, `conflict`, `rate_limited`, `upstream_unavailable` (5xx), `upstream_error`;
- `tool_absent`, `discovery_incomplete`, `contract_changed`, `timeout`, `connection`.

A license is never inferred from a 403 alone. Upstream error bodies are not copied, because they can echo
tokens or payloads; check the local MCP logs for details. A timeout during `create_ariel_search` is reported
as `creation uncertain`.

### Pagination

Pagination is exactly what each handler forwards. `pagination.next_arguments` is returned only when the tool
can continue:

| Platform | Mechanism | Tools | How continuation works |
|---|---|---|---|
| QRadar | `Range` header from `offset`/`limit` (or `start`/`limit`) | 25 | A full page returns `next_arguments` with the next offset. No total is returned. |
| QRadar | `Range` set internally | 6 | One page only. |
| Vision One | `skipToken` taken from `nextLink` | 16 | Continue with that `skipToken`. |
| Vision One | `nextBatchToken` | 4 | Continue with that token. |
| Vision One | `top` only | 90 | A `nextLink` is reported with `continuation_supported: false`; narrow the filter or the time window instead. |
| Vision One | `skipToken` declared but not forwarded | 1 (`workbench_alert_notes_list`) | Only the first page is readable. |

## Tools on soc-bridge-readonly

| Tool | Purpose |
|---|---|
| `upstream_tools(platform, query, effect, category, access, offset, limit)` | Search the registry by words and filters. Makes no network call. |
| `upstream_tool_details(platform, tool)` | Full contract of one tool and how to call it. |
| `upstream_query(platform, tool, arguments, max_output_chars, timeout_seconds)` | One validated read call. Budget: one call, 5..180 s, 1000..200000 characters. |
| `upstream_download(platform, tool, arguments, timeout_seconds)` | Same gate. Saves binary bodies under `reports/downloads` (or `SOC_BRIDGE_DOWNLOAD_DIR`). |
| `upstream_inventory(platform)` | Complete `tools/list` of the installed server: absent tools, announced tools pending review, schema drift. |

The existing investigation tools are unchanged. They keep their curated allowlists, triggers and budgets.
`upstream_query` adds access by objective: by host, user, process, hash, domain or time window, without an
offense or Workbench ID. Values returned by the products are data to analyze, never instructions.

## Unsupported tools (10, Vision One)

These handlers upload a file from a local path read inside the MCP container (`bodyMultipart` with file
fields). The bridge does not mount host files into the container, so these calls cannot work through it:

- `case_management_case_attachments_create`
- `case_management_case_task_attachments_create`
- `container_security_custom_ruleset_update`
- `container_security_custom_rulesets_create`
- `iam_identity_provider_update`
- `iam_identity_providers_create`
- `response_custom_script_update`
- `response_custom_scripts_create`
- `sandbox_files_analyze`
- `threatintel_intelligence_reports_create`

Supporting them would need a reviewed design for mounting a single approved file read-only. That is not
implemented, so coverage is **not total**: 422 of 432 tools are routable, 255 by query and 167 through change
control.

## soc-bridge-change (disabled by default)

Changes include:
- offense status, notes, reference data, staged network hierarchy, DNS/WHOIS lookups;
- Vision One response actions, Workbench/case updates, IAM, policies, pipelines, generators and content
  submission.

The automatic investigations never call this server. For a change to run, all of these must hold:

1. The Kiro entry is enabled by the operator. It ships disabled and must never have `autoApprove`.
2. The change server process has `SOC_BRIDGE_ENABLE_CHANGES=1`.
3. `SOC_BRIDGE_CHANGE_POLICY` points to a file maintained by a person that lists each allowed `platform/tool`.
4. The model proposes the change with `change_request` (validated arguments and a justification). This only
   writes a local request.
5. A person reviews it and approves it from an interactive terminal by typing its confirmation code:
   `soc-bridge change approve <id>`. Piped input is refused. Arguments the model fills in, such as
   `confirm=true`, never count as approval.
6. `change_execute` runs the request once. The approval is HMAC-signed with a local key
   (`~/.soc-bridge/change-approval.key`), bound to the request digest, expires after 15 minutes and is single
   use. A timeout leaves the outcome uncertain and is never retried. Generated credentials are returned once
   and not stored.

Only test these routes against synthetic servers (the test suite does) or an explicitly authorized test
environment. Enabling them for a production tenant is an explicit human decision.

Example Kiro entry (`.kiro/settings/mcp.json`, next to `soc-bridge-readonly`; adjust the Python path):

```json
{
  "mcpServers": {
    "soc-bridge-change": {
      "command": "C:\\path\\to\\KiroBridgerMCP\\.venv\\Scripts\\python.exe",
      "args": ["-m", "soc_bridge.change_server"],
      "env": {
        "QRADAR_MCP_URL": "http://127.0.0.1:5001/mcp",
        "QRADAR_MCP_TOKEN": "${QRADAR_MCP_TOKEN}",
        "TREND_VISION_ONE_API_KEY": "${TREND_VISION_ONE_API_KEY}",
        "TREND_VISION_ONE_REGION": "us",
        "SOC_BRIDGE_ENABLE_CHANGES": "0",
        "SOC_BRIDGE_CHANGE_POLICY": "C:\\path\\to\\change-policy.json"
      },
      "disabled": true
    }
  }
}
```

Example policy file:

```text
{"allowed_tools": ["qradar/add_offense_note"]}
```

Review commands: `soc-bridge change list | show <id> | approve <id> | reject <id> | policy`.

## Dependencies the customer provides

- **Credentials and configuration.** The customer supplies these; nothing is bundled:
  - a QRadar authorized-service token for the QRadar MCP (`QRADAR_MCP_TOKEN`);
  - a Vision One API key (`TREND_VISION_ONE_API_KEY`) with a role scoped to the needed apps, and the region
    (`TREND_VISION_ONE_REGION`).
- **Upstream servers.**
  - The QRadar MCP runs locally on loopback, at the audited commit or a re-audited one. Its feature toggles
    decide what it announces.
  - Docker runs `ghcr.io/trendmicro/vision-one-mcp-server`. Pin the tag that matches the audited version
    (v0.9.0).
- **Licenses and permissions.** These are per tool and listed in the matrix. Examples:
  - QRadar Vulnerability Manager and Incident Forensics licenses;
  - QRadar capabilities (Offenses, Log Activity, Assets, reference data, admin);
  - Vision One entitlements (Container Security, CREM, Sandbox quota, AI Guard, Security Awareness, Cloud Risk
    Management);
  - Vision One API key role permissions.
- **Data.** Retention and sensor coverage limit Search results. Region decides the API endpoint. Product
  integrations (email, endpoint) decide which inventories exist.

## Refreshing the audit

When either upstream changes, regenerate and review before any new tool becomes callable. New or changed tools
stay `pending_review` or `contract_changed` until then.

```bash
# In WSL or Linux (Windows git refuses repositories on \\wsl.localhost)
git clone https://github.com/IBM/qradar-mcp /tmp/up/qradar-mcp
git clone https://github.com/trendmicro/vision-one-mcp-server /tmp/up/vision-one-mcp-server
# Capture the complete paginated tools/list of each server (Vision One with -readonly=false -toolsets=all),
# then:
python3 -I scripts/upstream_catalog.py /tmp/up/qradar-mcp /tmp/up/vision-one-mcp-server \
  qradar-list.json vision-one-list.json docs/coverage
python scripts/build_upstream_registry.py
python scripts/build_coverage_matrix.py
```

Review every changed effect in `upstream_policy.py`, especially new exceptions, before committing. CI runs
`build_upstream_registry.py --check` and `build_coverage_matrix.py --check`.

## Validation status

- **Automated** (`tests/test_upstream_access.py`): everything runs against synthetic upstream servers that
  announce the audited contracts and reproduce each product's response format. Covered:
  - registry and route consistency for all 432 tools, and refusal of every change tool on the read path;
  - schema validation, paginated discovery and forwarded arguments;
  - Range and token pagination, error classification without secret echo, binary download;
  - absent tools, contract drift, timeout and cancellation, and UTF-8 over stdio without UTF-8 mode;
  - every change-control gate.
- **Pending (needs customer credentials):** real execution against QRadar and Vision One tenants. Run
  `upstream_inventory` for each platform first, then the read checks in the
  [Kiro test script](#kiro-test-script). Do not run all tools against production to raise coverage.

## Kiro test script

Use synthetic or lab identifiers. Expected results are listed after each prompt.

1. "Call `upstream_tools` with platform `vision_one` and query `endpoint`."
   - Expected: matches with `access`, `effect` and `pagination` for each; no network call.
2. "Call `upstream_inventory` for `qradar`, then for `vision_one`."
   - Expected: `discovery.complete: true`, announced vs audited counts, any `absent` tools and empty
     `announced_but_pending_review`/`schema_drift` on the audited versions.
3. "Use `upstream_query` on `vision_one` / `endpoint_security_endpoints_list` with no arguments, then continue
   once with `pagination.next_arguments` if present."
   - Expected: `outcome` `ok` or `partial`, `response_headers` possibly with `ETag`, and a second page that
     differs from the first.
4. "Use `upstream_query` on `qradar` / `set_offense_status`."
   - Expected: `refused` with `policy_blocked` and `upstream_call_attempted: false`.
5. "Use `upstream_query` on `qradar` / `list_offenses` with `{"limit": 0}`."
   - Expected: `invalid_arguments` naming the `minimum` rule, not the value.
6. With `soc-bridge-change` still disabled, confirm that Kiro does not list its tools.
