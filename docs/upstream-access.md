# Access to the upstream MCP tools

The bridge routes every tool of the audited versions of the [IBM QRadar MCP](https://github.com/IBM/qradar-mcp)
and the [Trend Vision One MCP](https://github.com/trendmicro/vision-one-mcp-server) through an audited
registry:

- **Read tools** run from `soc-bridge-readonly`.
- **Tools that change state, send data out or upload files** run only from a separate server,
  `soc-bridge-change`. It is disabled by default and needs a human approval for each call.

Routable does not mean proven to work. The evidence levels are kept separate:

| Audited version | Catalogued | Routed, query (enabled) | Routed, change (blocked by policy) | Unsupported | End-to-end (synthetic) | Real product |
|---|---|---|---|---|---|---|
| IBM QRadar MCP `60ca119` (2026-10-05) | 83 | 53 | 30 | 0 | 7 | 0 |
| Trend Vision One MCP `2d13740` (v0.9.0) | 349 | 202 | 147 (10 are file uploads) | 0 | 8 | 0 |

- **Contract checks** apply to all 432 tools. Each has a valid audited schema, equal to its announced contract,
  and exactly one route enforced by the gate. This does not execute the tool.
- **End to end:** only the 15 tools in the [coverage matrix](coverage-matrix.md) "End-to-end" column were called
  through the bridge, against synthetic MCP servers. The other 417 are routed and contract-checked but not
  exercised end to end.
- **Real product:** no `upstream_*` call has been executed against a real tenant (see
  [Validation status](#validation-status)).
- **Installation availability:** the totals describe the audited code, not what a given installation, license or
  API key allows. `upstream_inventory` and the error categories report that at run time.

## Architecture

```text
Kiro ── soc-bridge-readonly ── upstream_tools / upstream_tool_details   (registry search, no network)
                            ├─ upstream_query / upstream_download      (gate → one upstream session → one call)
                            └─ upstream_inventory                      (complete tools/list vs registry)
Kiro ── soc-bridge-change (disabled) ── change_request → human approves in a terminal → change_execute
```

### Registry

`src/soc_bridge/upstream_registry.json` is generated by `scripts/build_upstream_registry.py` from three inputs:

- the handler catalogs (`docs/coverage/*-mcp-tools.json`), which `scripts/upstream_catalog.py` extracts without
  importing or running upstream code;
- the complete paginated `tools/list` of each server (`docs/coverage/*-tools-list.json`);
- the pinned Vision One image evidence (`docs/coverage/vision-one-image.json`).

For each tool it records:

- the effect and its basis, and the access path;
- the validation schema (for QRadar, the handler schema with its ranges and enums);
- the announced schema, used for drift checks;
- the HTTP method and path;
- the pagination the handler actually forwards;
- the output format, upload facts and dependencies.

### On-demand dispatch

The bridge uses one dispatcher instead of one MCP tool per upstream tool:

- The 432 schemas take about 410 KB, which would crowd the model context in every Kiro session.
- One dispatcher keeps a single gate: exact names, schema validation, effect policy and contract checks.
- Kiro configures `autoApprove`/`disabledTools` per server, so read tools and change tools live on separate servers.
- The two catalogs share no names, and the `platform` argument namespaces every call.

### Effect policy

`src/soc_bridge/upstream_policy.py` decides each effect from the handler, never from the name, a verb or
`readOnlyHint` alone.

QRadar:

- A `GET` that only calls `client.get` and is not marked approval-required is a read.
- `validate_aql` is validation, and `create_ariel_search` is a search job.
- `dns_lookup` and `whois_lookup` send the value to external services, so they are changes.

Vision One:

- A tool registered as read that issues `GET` is a read.
- Ten tools registered as read post data, so they are changes: seven generators, one credential generator and
  `aisecurity_guardrails_apply`.
- Tools whose handler uploads a local file are changes that need the [upload flow](#file-uploads).
- Anything else is `pending_review` and cannot be called.

### Pinned versions

- **Vision One.** Inventory, queries and changes always start
  `ghcr.io/trendmicro/vision-one-mcp-server@sha256:91e8a673c94a5612f145d6a23f14c9a1b712ec8eb2345202b5e8310661408b67`.
  - That is the index digest of tag `v0.9.0`. Its OCI labels (`org.opencontainers.image.revision`) and BuildKit
    provenance (`vcs:revision`) name the audited commit `2d137401c26e7c50345d448ea1c662746cb2e7a9`.
  - The curated investigation workflows and `soc-bridge doctor` use the same reference.
  - This is registry metadata checked with `docker buildx imagetools inspect`. The image was not rebuilt from
    source to compare binaries.
  - Responses carry `version_binding` with the image and the audited commit.
- **QRadar.** The QRadar MCP is installed and run by the operator, so the bridge cannot verify which version is
  running. `version_binding.verified` is `false`. Matching `tools/list` and schemas does not prove that handler
  effects are unchanged, so keep the QRadar MCP at the audited commit.
- **QRadar access path.** The bridge only talks to a loopback `http://127.0.0.1:<port>/mcp`, with proxies ignored.
  The QRadar MCP has no read-only mode, so the gate is the only barrier on the read path.
- **Vision One containers.**
  - Each query starts the image with `-readonly=true` and only the requested tool's toolset, so no write tool is
    registered.
  - Change calls start it without `-readonly`, except read-registered generators.

### Per-call checks (`upstream_query`)

1. **Name.** The platform is `qradar` or `vision_one`, and the tool name matches exactly
   (`^[a-z0-9_]{1,80}$`). There is no normalization, prefix, path or lookalike character.
2. **Effect.** The tool is in the registry, verified and supported, and its effect is `read`, `validation` or
   `query_job`. Otherwise the call is refused with `upstream_call_attempted: false` and no session is opened.
3. **Arguments.** Arguments are validated against the audited schema:
   - unknown properties are rejected;
   - the limit is 64 KB;
   - errors name the rule, never the value;
   - a parameter that the handler declares but does not send is refused (`workbench_alert_notes_list.skipToken`).
4. **Discovery.** The complete paginated `tools/list` must finish. If any page fails, repeats a cursor or hits the
   page or time cap, the result is `discovery_incomplete` and no call is made. That holds even when the tool
   appeared on a page that was read.
5. **Contract.** The tool must be announced (`tool_absent` otherwise). Its announced schema must match the audited
   one under a recursive comparison:
   - types, `required`, `enum`/`const`, bounds and lengths;
   - `pattern`/`format`, nested `properties`/`items`/`additionalProperties`;
   - `anyOf`/`oneOf`/`allOf` (order-insensitive), `$ref`/`$defs` and `default`.

   Only descriptive keywords are ignored: `description`, `title`, `examples`, `$comment` and `x-*`. Any
   difference returns `contract_changed` with the paths, and no call is made. An equal schema still does not
   prove that the handler's effect is unchanged.
6. **Call.** Exactly one `tools/call` is made, followed by output normalization (next section).

### Output limit, partial pages and continuation

- **Limit.** `max_output_chars` (1000..200000, default 50000) bounds the JSON of the `data` field. The envelope
  (arguments echo, pagination, provenance) is outside that limit.
- **What is kept.** Items are kept whole and in order. Large non-item fields are replaced by an
  `[omitted by the bridge: N characters]` marker listed in `fields_omitted`. Continuation and identifier fields
  are kept: `nextLink`, `nextBatchToken`, `totalCount`, `count`, `id` and `status`.
- **Item counts.** `items_returned` (`items_in_response`), `items_delivered`, `items_omitted` and `items_skipped`
  state exactly what the product returned and what was delivered.
- **Partial delivery, Range pagination (QRadar).** When the bridge delivered part of a page,
  `pagination.next_arguments` starts at the first item not delivered (`offset + items_delivered`), so nothing is
  skipped.
- **Partial delivery, token and single-page tools.**
  - `pagination.next_arguments` is withheld.
  - `pagination.recover` gives the same arguments with `skip_items`. Call `upstream_query(..., skip_items=N)` to
    receive the rest of the page; the page is read again and may have changed upstream.
  - `pagination.next_page_arguments` follows only after recovery.
- **Empty pages.**
  - An empty page with `nextLink`/`nextBatchToken` is `partial`, not `empty`.
  - When the handler cannot continue (`continuation_supported: false`), narrow the filter or time window.
  - `empty` means a terminal empty page for that query, filter and window. It is not proof of absence elsewhere.

### Outcomes and error categories

| Outcome | Meaning |
|---|---|
| `ok` | Complete response for these arguments. |
| `partial` | More data is indicated, or the bridge delivered part of the response. |
| `empty` | A terminal empty page for this query, filter and window. |
| `empty_response` | The call succeeded with no content. |
| `error` | See the categories below. Errors are never turned into empty lists. |
| `refused` | Not sent upstream (`policy_blocked`, `unknown_tool`, `pending_review`, `unsupported`, `invalid_arguments`, `configuration`). |

Error categories:

- **From the product's answer:**
  - `invalid_arguments` (HTTP 400/422 or a known validation message), `authentication` (401);
  - `permission` (403), `permission_or_license` (403 whose body mentions a license or entitlement);
  - `not_found`, `conflict`, `rate_limited`, `upstream_unavailable` (5xx), `upstream_error`.
- **Before the call:** `tool_absent`, `discovery_incomplete`, `contract_changed`.
- **After the request was sent:** `timeout` and `connection_lost_or_invalid_response`. These carry
  `error.result_state: unknown`, because the upstream may have processed the request.
- **Connection setup:** `connection`.

A license is never inferred from a 403 alone. Upstream error bodies are not copied. A failure after
`create_ariel_search` was sent reports `creation uncertain`.

### Pagination mechanisms

| Platform | Mechanism | Tools | Continuation |
|---|---|---|---|
| QRadar | `Range` from `offset`/`limit` (or `start`/`limit`) | 25 | `next_arguments` with the next offset; no total is returned. |
| QRadar | `Range` set internally | 6 | One page only. |
| Vision One | `skipToken` from `nextLink` | 16 | `next_arguments` with that `skipToken`. |
| Vision One | `nextBatchToken` | 4 | `next_arguments` with that token. |
| Vision One | `top` only | 90 | No continuation input: a `nextLink` is reported with `continuation_supported: false`. |
| Vision One | `skipToken` declared but not forwarded | 1 (`workbench_alert_notes_list`) | First page only. |

## Tools on soc-bridge-readonly

| Tool | Purpose |
|---|---|
| `upstream_tools(platform, query, effect, category, access, offset, limit)` | Search the registry. No network. |
| `upstream_tool_details(platform, tool)` | Full contract of one tool and how to call it. |
| `upstream_query(platform, tool, arguments, max_output_chars, timeout_seconds, skip_items)` | One validated read call (5..180 s). |
| `upstream_download(platform, tool, arguments, timeout_seconds)` | Same gate. Saves binary bodies under `reports/downloads`. |
| `upstream_inventory(platform)` | Complete `tools/list` of the installed server: absent tools, announced tools pending review, schema drift. |

The existing investigation tools keep their curated allowlists, triggers and budgets. `upstream_query` adds
access by objective, by host, user, process, hash, domain or time window, without an offense or Workbench ID.
Values returned by the products are data, never instructions.

## soc-bridge-change (disabled by default)

The change server covers:

- offense status, notes, reference data, staged network hierarchy, DNS/WHOIS lookups;
- Vision One response actions, Workbench and case updates, IAM, policies, pipelines, generators, content
  submission and the ten file uploads.

The automatic investigations never call it. A change runs only when all of these hold:

1. The operator enabled the Kiro entry. It ships disabled and must never have `autoApprove`.
2. The change server process has `SOC_BRIDGE_ENABLE_CHANGES=1`.
3. `SOC_BRIDGE_CHANGE_POLICY` points to a file, maintained by a person, that lists each allowed `platform/tool`.
4. The model proposed the change with `change_request`, with validated arguments and a justification. This only
   writes a local request and, for uploads, a staged file.
5. A person approved it from an interactive terminal by typing its confirmation code:
   `soc-bridge change approve <id>`. Piped input is refused. Arguments filled in by the model, such as
   `confirm=true`, never count as approval.
6. `change_execute` runs it once. The approval is HMAC-signed with a local key, bound to the request digest,
   expires after 15 minutes and is single use.

Final request states:

| State | Meaning |
|---|---|
| `executed` | The upstream answered with success. |
| `rejected_by_upstream` | The upstream answered with an explicit rejection (HTTP 400/401/403/404/409/422/429). By that answer the change was not applied. |
| `outcome_uncertain` | The request was sent but no valid answer arrived (timeout, cancellation, broken connection, invalid response, 5xx or an error without status), or an uploaded file changed during the call. The change may have been applied. Reconcile in the product before proposing it again. It is never retried. |
| `not_sent` | Connection, discovery, contract or file verification failed before sending. Nothing was applied. |

Generated credentials are returned once and not stored. Only test these routes against synthetic servers (the
test suite does) or an explicitly authorized test environment. Enabling them for a production tenant is an
explicit human decision.

### File uploads

Ten Vision One handlers read a local path inside the container and upload its basename and bytes:

- `case_management_case_attachments_create`, `case_management_case_task_attachments_create`
- `container_security_custom_ruleset_update`, `container_security_custom_rulesets_create`
- `iam_identity_provider_update`, `iam_identity_providers_create`
- `response_custom_script_update`, `response_custom_scripts_create`
- `sandbox_files_analyze`, `threatintel_intelligence_reports_create`

The bridge supports them only through `soc-bridge-change`.

1. **Proposal.** `file` must be an absolute path to a regular file of at most 64 MiB.
   - Relative paths, directories, devices, symbolic links and paths through a link or Windows junction are refused.
   - The file is opened without following links, checked to be the same file that was inspected, and copied into
     a private staging folder: `reports/changes/staged/<request-id>/`, mode 0700/0400 on POSIX.
   - Its SHA-256, size, sanitized name and container path `/approved/<name>` enter the request digest. The
     approval therefore covers the destination, the arguments and the exact bytes.
2. **Approval.** The terminal shows the source path, size, SHA-256 and destination.
3. **Execution.**
   - The staged copy is hashed again. If it changed, the request becomes `not_sent` and nothing is sent.
   - The copy is bind-mounted read-only as a single file:
     `--mount type=bind,source=<staged file>,target=/approved/<name>,readonly`.
   - The `file` argument is replaced by `/approved/<name>`.
   - After the call the copy is hashed again (a change means `outcome_uncertain`), then the staging folder is
     removed.
   - The source file is never read again after the proposal, and no user directory is mounted.
4. **Cleanup.** Rejection and expiry also remove the staging folder.
5. **Windows and WSL.** The staged path belongs to the environment that runs the bridge and Docker. On Windows
   with Docker Desktop that is a Windows path. In WSL it is a Linux path, and source files on Windows drives must
   be given as `/mnt/c/...`. Paths with commas or quotes are refused, because they cannot be expressed safely in
   `--mount`.
6. **Residual risk.** A process running as the same user could replace the staged copy between the last
   verification and the container's read. The post-call verification turns that case into `outcome_uncertain`.
   It does not prevent it.

Tests use synthetic files and a synthetic server that reads the emulated mount. No real file is uploaded.

### Kiro entry

Add it next to `soc-bridge-readonly` in `.kiro/settings/mcp.json`, and adjust the Python path:

```json
{
  "mcpServers": {
    "soc-bridge-change": {
      "command": "C:\\path\\to\\KiroBridgerMCP\\.venv\\Scripts\\python.exe",
      "args": ["-m", "soc_bridge.change_server"],
      "env": {
        "QRADAR_MCP_URL": "http://127.0.0.1:5001/mcp",
        "QRADAR_MCP_TOKEN": "${QRADAR_MCP_TOKEN}",
        "TREND_VISION_ONE_API_KEY": "${TREND_VISION_ONE_API_KEY}",
        "TREND_VISION_ONE_REGION": "us",
        "SOC_BRIDGE_ENABLE_CHANGES": "0",
        "SOC_BRIDGE_CHANGE_POLICY": "C:\\path\\to\\change-policy.json"
      },
      "disabled": true
    }
  }
}
```

Policy file example:

```text
{"allowed_tools": ["qradar/add_offense_note"]}
```

Review commands: `soc-bridge change list | show <id> | approve <id> | reject <id> | policy`.

## Dependencies the customer provides

- **Credentials and configuration.** The customer supplies these; nothing is bundled.
  - QRadar authorized-service token (`QRADAR_MCP_TOKEN`).
  - Vision One API key (`TREND_VISION_ONE_API_KEY`), with a role scoped to the needed apps, and the region
    (`TREND_VISION_ONE_REGION`).
- **Upstream servers.**
  - The QRadar MCP runs locally on loopback, at the audited commit.
  - Docker pulls the pinned Vision One digest on first use, which needs registry access or a mirror holding that
    digest.
- **Licenses and permissions.** These are per tool and listed in the matrix. Examples:
  - QRadar Vulnerability Manager and Incident Forensics;
  - QRadar capabilities;
  - Vision One entitlements: Container Security, CREM, Sandbox quota, AI Guard, Security Awareness, Cloud Risk
    Management;
  - API key roles.
- **Data.** Retention and sensor coverage limit Search. The region decides the API endpoint.

## Refreshing the audit

When either upstream changes, regenerate and review everything before a new version becomes callable. New or
changed tools stay `pending_review` or `contract_changed` until then.

```bash
# In WSL or Linux (Windows git refuses repositories on \\wsl.localhost)
git clone https://github.com/IBM/qradar-mcp /tmp/up/qradar-mcp
git clone https://github.com/trendmicro/vision-one-mcp-server /tmp/up/vision-one-mcp-server
# Capture the complete paginated tools/list of each server (Vision One with -readonly=false -toolsets=all), then:
python3 -I scripts/upstream_catalog.py /tmp/up/qradar-mcp /tmp/up/vision-one-mcp-server \
  qradar-list.json vision-one-list.json docs/coverage
docker buildx imagetools inspect ghcr.io/trendmicro/vision-one-mcp-server:<tag>
# Record the index digest, both platform digests, label and provenance revision in docs/coverage/vision-one-image.json
python scripts/build_upstream_registry.py   # refuses an image whose revision is not the audited commit
python scripts/build_coverage_matrix.py
```

Review every changed effect in `upstream_policy.py` before committing. CI runs
`build_upstream_registry.py --check` and `build_coverage_matrix.py --check`.

## Validation status

**Automated.** These tests use synthetic servers and files only:

- `tests/test_upstream_access.py` covers:
  - registry and route consistency for all 432 tools;
  - refusal of every change tool on the read path;
  - schema validation, paginated discovery and argument forwarding;
  - pagination, error classes without secret echo, binary download;
  - absent tools, drift, timeout and cancellation, and UTF-8 without UTF-8 mode;
  - the change-control gates.
- `tests/test_upstream_regressions.py` covers:
  - incomplete discovery blocking a first-page tool, with zero calls;
  - recursive contract changes, including `anyOf` and nested objects;
  - the output limit on arbitrary shapes, and continuation after a local cut for Range and token tools;
  - empty pages with and without continuation;
  - the pinned image in queries and inventory;
  - uncertain outcomes after a broken connection, timeout, cancellation and 5xx;
  - staged uploads: exact bytes, single read-only mount, replaced file, unsafe paths, cleanup.

**Pending.** These need customer credentials:

- real execution against QRadar and Vision One tenants;
- a real pull of the pinned digest by the customer's Docker.

Run the read-only [Kiro test script](#kiro-test-script) first. Do not run all tools against production to raise
coverage.

## Kiro test script

This script is read-only. Use synthetic or lab identifiers.

1. Ask: "Call `upstream_inventory` for `qradar`, then for `vision_one`."
   - **Expected:** `discovery.complete: true`, announced and audited counts, `absent` listing the tools your
     installation does not expose, and empty `announced_but_pending_review` and `schema_drift`.
   - **If it fails:** `discovery_incomplete` or `connection` points to the MCP setup. Drift means the installed
     version differs from the audited one.
2. Ask: "Call `upstream_tools` with platform `vision_one` and query `endpoint`, then `upstream_tool_details` for
   `endpoint_security_endpoints_list`."
   - **Expected:** registry data only, with no network call.
3. Ask: "Call `upstream_query` on `vision_one` / `endpoint_security_endpoints_list` with no arguments and
   `max_output_chars` 2000."
   - **Expected:** `ok` or `partial`, `version_binding.image` with the pinned digest, and `items_delivered`.
   - If `pagination.recover` appears, call it with `skip_items` before using `next_page_arguments`.
4. Ask: "Call `upstream_query` on `qradar` / `list_offenses` with `{"limit": 5}`, then continue once with
   `pagination.next_arguments`."
   - **Expected:** `version_binding.verified: false` for QRadar, and offsets that continue without gaps.
5. Ask: "Call `upstream_query` on `qradar` / `set_offense_status`."
   - **Expected:** `refused` / `policy_blocked`, and `upstream_call_attempted: false`.
6. Ask: "Call `upstream_query` on `qradar` / `list_offenses` with `{"limit": 0}`."
   - **Expected:** `invalid_arguments` naming the `minimum` rule, not the value.
7. Confirm that `soc-bridge-change` is not listed as connected in Kiro.

If these pass, record the date, versions and outcomes. Then extend the read checks to the tools the analysts
actually need, one objective at a time. Enabling `soc-bridge-change` in a test tenant is a separate, explicit
decision.
